# 视频规律卡顿根因定位与修复（b7b3a17 音频紧循环饿死视频解码）

日期：2026-11-24

## 现象

同一块板：烧 `824ffcf`（main 分支）播放视频不卡；烧 `eb4aa45`（main-screen-v2 分支）播放视频有规律卡顿。卡顿周期约 130 ms，即 30 fps 下每 4 帧卡一次。

## 根因

单一提交 `b7b3a17`（"fix: 缓解视频并发下音频供数不足"，2026-10-06）同时做了两件事，叠加饿死视频解码：

1. 音频服务循环从固定 5 ms 节拍改为 `taskYIELD()` 紧循环（仅 `PLAYER_BUSY` 才 delay 1 ms）。
2. I2S DMA 缓冲从 `6×240` 帧加大到 `12×480` 帧（44.1 kHz 单声道下约 33 ms → 130 ms）。

## 机制

- 音频任务（CPU1，优先级 5）与视频 JPEG 解码任务（CPU1，优先级 4）**同核**。
- `taskYIELD()` 在音频是最高优先级就绪任务时不发生切换，音频任务退化为紧循环。
- I2S 缓冲每 ~130 ms 排空一次，音频任务在 write 阻塞前会**连续软解 MP3 填满缓冲**——这段是纯 CPU 计算、非阻塞，以优先级 5 独占 CPU1，饿死优先级 4 的视频解码。
- 视频 tick（CPU0）等不到解码结果，帧输出延迟 → 每 ~130 ms 规律掉帧。
- 缓冲填满后音频阻塞在 I2S write 让出 CPU，视频恢复；如此循环。

## 证据（824ffcf vs eb4aa45 实测对比）

| 项 | 824ffcf（不卡） | eb4aa45（卡） |
|---|---|---|
| 音频循环 | `vTaskDelay(active ? 5 : 50)` | `taskYIELD()` + `vTaskDelay(1ms)` |
| I2S DMA | `6×240` 帧 | `12×480` 帧 |
| 帧时间戳 | 旧（rate gate 后推进） | 新（LCD gate 后推进，`89d7095`） |
| 面板 init | 默认 jd9855 | `screen_v2_init.h` |

时间戳改动（`89d7095`）与 screen-v2 面板 init 已排除：前者稳定态两版等价（host 对照见 `VIDEO_STUTTER_202611_FRAME_GATE.json`）；后者时序寄存器（0xB7/0xC0/0xC3/0xC4/0xD3/0xD5/0xD6/0xD7）与默认序列逐字节相同。

## 修复

只改一处（单变量）：`main/audio_player.c` 的 `audio_service_task()` 恢复固定节拍。

```c
// 修复前
else if (result == PLAYER_BUSY) vTaskDelay(pdMS_TO_TICKS(1));
else                            taskYIELD();
// 修复后
else                            vTaskDelay(pdMS_TO_TICKS(1));
```

保留 b7b3a17 的初衷（加大 I2S 缓冲防音频断流），只去掉紧循环副作用。未动优先级、时间戳、缓冲大小。

## 上一轮排查为何漏掉它

1. **基线选错**：以"11 月前(`74a8b78`) vs 11 月后(`f9d3086`)"为分界，把 10-06 的 `b7b3a17` 归入"基线背景"排除；而真正可区分的两版（`824ffcf` vs `eb4aa45`）差异恰好包含它。
2. **没用二分**：用户手里有"不卡 vs 卡"两个具体 commit，是最强证据；上一轮没要求/没利用，而是自行从 11 月提交里猜。
3. **误判 taskYIELD 危害**：认为"I2S write 等待时会让出 CPU"，据此弱化音频竞争；但 buffer 加大到 130 ms 后，"连续解码填缓冲"是纯计算、非阻塞、独占 CPU1。
4. **最高优先级结论未做 A/B 证伪**：profile 同步日志（64 ms 模型预算）被列为最确定风险，但 profile 两版都存在、不是差异点，不可能解释这个二分。
