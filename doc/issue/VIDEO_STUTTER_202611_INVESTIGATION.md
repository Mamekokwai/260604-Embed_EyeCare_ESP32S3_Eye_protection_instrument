## 三、关键实验结果

### 1. 同步日志预算

源码位置：`main/video_player.c` 的 `frame_count % PROF_EVERY == 0` 分支，`PROF_EVERY=100`。当前 `sdkconfig` 为 INFO、默认 UART 控制台 115200，另有 USB Serial-JTAG 次控制台。

本机 ESP-IDF v5.4.4 的源码证据：

1. `components/log/src/os/log_write.c` 默认使用 `vprintf`，应用没有替换此函数。
2. `components/esp_vfs_console/vfs_console.c` 的 `console_write()` 同步写主、次控制台。
3. `components/esp_driver_uart/src/uart_vfs.c` 默认 `tx_func=uart_tx_char`；`uart_write()` 逐字符发送，`uart_tx_char()` 在 FIFO 不足时轮询等待。
4. 应用没有将 UART0 控制台切换为异步日志服务。CA51→JTAG 的异步转发队列是另一条路径，不能让 `ESP_LOGI()` 变成异步。

738 B 是本次格式化样例，数值宽度和时间戳不同会改变长度；64.06/52.95 ms 是 UART 传输预算，未包含格式化、日志锁、USB 次控制台等待、其他任务抢占。不能把它写成“已测得客户卡顿64ms”。

单帧被拖长后，绝对deadline策略可能压缩后续帧间距以追赶，所以100帧平均仍可能接近30fps。**平均FPS合格不足以排除肉眼可见的某一帧停顿。**

### 2. 帧时间戳修改前后

| 场景 | 11月前代码 | 当前代码 |
| --- | --- | --- |
| LCD一直可用，连续100帧 | 按33333us周期，通过 | 同样周期，通过 |
| 首次gate忙，1000us时可用 | 33333us才提交 | 1000us可提交 |
| 第二帧33333us gate忙，35000us可用 | 错推deadline至66666us，继续等 | 35000us立即提交，deadline只推进一次 |
| 模拟晚了2s | 逐帧追赶，deadline不重置 | 相同政策 |

因此当前源码不支持把 `500be5b` 当作首要回退目标。测试使用真实源代码片段、模拟时钟和LCD就绪信号，不是运行在ESP32上的时延测量。
